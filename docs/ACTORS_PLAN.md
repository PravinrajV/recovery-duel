## 2. Proposals

### A1 (recommended, verified): Document Reader + inline validation + human validation

**What it is.** For the claim picked for recovery, the flow takes a SYNTHETIC repair estimate PDF from the shop (generated by us from `data/claims.csv`). A Document Reader agent extracts the fields with the built-in Analyze Files tool. A script validates them against the claim record. If any rule fails or confidence is low, a person validates the fields in Action Center before the case moves on. Validated facts (estimate number, repair total, loss cause on the estimate) are cited in the evidence memo and the demand letter.

**Actors added:** AI agent (document reading), deterministic validation, document extracted and validated inline, human validation.

**Where it plugs in** (`.flow-sdk/RecoveryDuel.flow.ts`):
- Input: add `estimateFile: types.file` to `.input(...)`. If Flow rejects a run without it (unverified, see risks), the harness always attaches a file and the flow treats a missing or blank file name as `DOC_NOT_PROVIDED`.
- Between `pickTop` (after the `noCase` branch) and `evidenceAnalyst`, insert:
  1. `docReader`: `inlineAgent({ model: 'anthropic.claude-sonnet-4-6', temperature: 0, tools: [{ kind: 'builtin', tool: 'analyzefiles' }], inputs: { estimate: input('estimateFile') }, returns: { claim_id, vin, estimate_no, loss_cause, parts, labor, other, subtotal, tax, total, confidence, notes } })`. One return field per value (the probe returned one text field, and on the tampered PDF the agent added prose to it, so separate typed fields are cleaner). `.onError` -> `docStatus = DOC_ERROR`, continue.
  2. `docValidate`: script, pure function shared with a new `rules/doc_rules.js` so it is unit tested offline. Rules: claim ID equals the picked claim; VIN equals the claim VIN; parts + labor + other = subtotal (within $1); subtotal + tax = total (within $1); total within 5% of `paid_amount + deductible`; `confidence >= 0.8`; any instruction-like text in `notes` or fields ("ignore", "set floor", "demand") is flagged `DOC_INJECTION` and never used. Output `VALIDATED`, `NEEDS_HUMAN_VALIDATION` (with the failed checks listed) or `DOC_NOT_PROVIDED`.
  3. `.branch('docNeedsHuman', ...)` -> `docValidation`: `hitl({ variant: 'quick-form', title: 'Recovery Duel: validate SYNTHETIC repair estimate', fields: extracted values as `inOut`, failed checks as read-only, outcomes: ['Accept', 'Reject'] })` with `.stepSwitch`. Accept -> re-run `docValidate` on the corrected values in "human" mode (records `validated_by: HUMAN`). Reject -> `docStatus = DOC_REJECTED`, and the case continues on rules and recall data only, with the letter saying the estimate is under review.
  4. Pass `docFacts` into `evidenceAnalyst` and `liabilityAssessor` inputs and into the `letter` script. The rules engine still owns every dollar: the document never changes demand or floor. It only adds facts and can raise a human check.
- Outputs: add `document: { status, validated_by, checks, facts }` to the flow output and the ledger entry (`book`).

**Risks.**
- Agent extraction is not a trained DU model. We say so plainly: "LLM document extraction with rule validation; Document Understanding is not provisioned on this Community tenant." Mitigation: temperature 0, typed fields, rules own the decision, human validation on any failure.
- Whether a `types.file` input can be left empty on a run is unverified. Mitigation: always attach a file in the harness; a "no estimate on file" PDF variant covers the missing case.
- Bucket-sourced runs (`source: bucket`) have no file attachment. Mitigation: for bucket runs, `DOC_NOT_PROVIDED` and no document step (documented), or pass the file at trigger time.
- AI unit use: one extra agent call per run. The same model already runs 4+ times per run, so this is small. Credits are not visible by CLI (owner checks Admin > Licenses).
- Injection text in a document: handled by rule 7 and tested in S14, same as the email injection.

**Effort:** about 4 to 6 hours (PDF generator 1h, rules + tests 1h, flow edit + compile 1.5h, harness + 5 tenant runs 1.5h, docs 0.5h).

### A2 (conditional, unverified): Data Fabric entity `RecoveryCase`
**What:** one native entity with one record per run and claim: `ClaimId`, `RunId`, `Status`, `Demand`, `Floor`, `SettledAmount`, `Tier`, `Approval`, `DocStatus`, `DocValidatedBy`, `Rounds`, `Synthetic` (always true), `SimulatedCounterparty` (always true). The bucket ledger stays as the fallback, so nothing breaks if DF is down.
**Where:** after `book`, next to `ledgerAppend`: `dataFabricCreate({ entity: 'RecoveryCase', ... })` with `.onError` -> `dfWrite = { ok: false }`; and at intake, an optional `dataFabricRead({ entity: 'RecoveryCase', resultMode: 'multiple', filters: [{ field: 'ClaimId', value: ... }] })` to skip claims already settled (a real reason to read it).
**Commands:** `uip df entities list` (must succeed first), `uip df entities create RecoveryCase --file docs/df/RecoveryCase.json`, `uip df entities get RecoveryCase` (resolve columns, since wrong columns are dropped silently), then flow check/compile/validate/debug as above, and `uip df records list <entity-id>` to show the rows.
**Feasibility:** NOT verified. The service is now Enabled but "setup is still in progress". Next check: re-run `uip df entities list` in Phase 2. If it still fails after a day, we drop A2 and the submission says "data held in an Orchestrator storage bucket because Data Fabric was not available on this Community tenant".
**Risks:** provisioning may never finish on Community; entity limits unknown; silent column drops (mitigated with `df entities get` and a `df records list` check).
**Effort:** about 2 to 3 hours once `df entities list` works.
